# CC 与 GD 端侧 3B 数据集评审与训练前整改建议

## 结论先行

当前 CC 和 GD 数据集适合验证数据工厂、训练格式、确定性后处理和端到端渲染流程，暂时不适合作为正式模型泛化能力的证明。

两套数据都存在同一个核心问题：输入由固定句式批量扩展，字段或语素标签直接代入句子。模型可以依靠字段名、短语和句式完成映射，却未必真正理解自然语言中的近义表达、隐含意图、否定、纠正和不支持请求。

因此，当前数据应明确标记为：

> **synthetic bootstrap dataset：用于工程打通和回归，不用于对外宣称自然语言准确率。**

它不需要删除。更稳妥的做法是保留现有数据作为工程回归集，同时补建自然语言训练集和独立冻结评测集。

## 本次核验的事实

### CC

当前数据位于 `training/datasets/cc-3b-v1/`：

- 总样本：4200 条；
- 第一层：3360 条；
- 第二层：840 条；
- train/dev/test：2744/1010/446；
- 数据来源：CreateMyCard provider gallery；
- 第一层目标：能力、字段、主题和动作；
- 第二层目标：候选方案中的数字编号；
- 中间 Search 由代码执行，没有作为模型输入。

CC 的生成器按 `(businessId, scenarioId)` 做稳定分组，且另外留出了整组组合。这一点能够避免同一个案例直接跨越 train/dev/test，是正确的工程设计。

但查询文本仍由固定模板产生，例如“做一张……卡片”“我想在桌面看看……”“请把……放到一张卡片里”。此外，部分查询把能力注册表或实现过程直接写进用户话语，例如：

> 显示应用名称、使用时长、端侧完成数据查询和归一化的时间。

这类句子更像内部 schema 描述，不像普通用户请求。

### GD

当前数据位于 `data/datasets/gd-morpheme-3b-v1/`：

- 总样本：3636 条；
- 101 个确定性骨架；
- train/dev/test：2736/432/468；
- 每条样本都是单轮语素规划；
- 输出只包含 `t` 和 `m[l,q,f,r]`；
- 数据来自当前能力注册表；
- 实习生 V4 Frame 数据没有混入语素 SFT。

GD 按 `skeleton_id` 做稳定切分，因此同一个骨架不会跨 split。这能避免最直接的样本复制，但每个骨架仍然使用同一套约 36 个固定句式。典型样本包括：

```text
帮我看看电量。
我想在卡片上看到电量。
做一张电量卡片。
桌面显示电量就行。
```

这类样本适合验证“已知字段能否输出成规定格式”，不能单独验证模型是否能理解“手机还剩多少格电”“电池快没了”等自然表达。

## 三个主要问题

### 1. 数据更像模板填空，而不是自然语言理解

当前生成逻辑是：

```text
固定句式 + 字段中文标签 + 固定动作后缀
                         ↓
                    标准语素答案
```

这会让模型学习到表面捷径：

```text
出现“电量” → phone.battery.level
出现“蓝牙开关” → bluetooth.power
出现“下一个日程” → calendar.next_event
```

而不是学习更稳健的语义等价关系：

```text
“手机还剩多少格电啊”
“电池还能撑多久”
“下个会议几点开始”
“别显示湿度，只看温度”
```

当前数据仍然有训练价值，主要集中在：

- JSON 或 DSL 的格式学习；
- 输出字段和类型的结构学习；
- 注册表内的键映射；
- CC 第二层编号选择；
- 确定性编译器和渲染器的回归。

它不能单独证明：

- 近义词泛化；
- 口语理解；
- 否定和纠正；
- 多意图拆分；
- 未注册能力拒答；
- 不应添加动作时的克制。

### 2. train/dev/test 没有完全解决语义泄漏

当前切分不是简单的按行随机切分，CC 和 GD 都做了组级切分，这是优点。

但“同组不跨 split”不等于“语义不泄漏”。不同组之间仍然复用：

- 同样的固定句式；
- 同样的字段中文标签；
- 同样的动作表达；
- 相同或高度相似的字段组合；
- 相同的答案结构。

因此，当前 dev/test 主要测量：

> 在已知任务形状和已知表达模板下，模型能否稳定输出正确结构。

它不适合作为纯自然语言泛化分数。

仓库检查还发现，CC 的不同 split 之间存在少量完全相同的用户请求文本。这说明后续需要增加文本级和近重复级去重，而不能只依赖案例组切分。

对于 Claude 提到的“训练后 test 达到 95%+”，应保留原始实验配置、模型版本、温度、提示词版本、是否使用约束解码和评分脚本。当前数据本身不足以证明这个数字代表真实泛化能力。更合理的做法是把它标记为“合成同分布测试分数”，并与独立冻结集分数分开报告。

### 3. CC 的部分用户话语包含实现语言

CC 的字段描述来自 gallery 和注册表。自动生成时，字段描述会进入用户查询，导致以下内容被当成用户意图：

- 端侧完成数据查询；
- 数据归一化时间；
- 指定应用的内部查询过程；
- 带有 schema 含义的内部字段说明。

这会给模型提供答案线索，也会改变训练分布。线上用户通常不会用同样的术语表达需求。

处理这类样本时，不能只做机械同义词替换。必须确认改写后的自然语言确实与字段语义等价。例如：

```text
内部描述：端侧完成数据查询和归一化的时间
候选改写：数据更新到什么时候
```

候选改写需要人工确认，因为“数据更新到什么时候”是否等价于 `updatedAt`，取决于产品真实语义。

## 对现有方案的评价

### 值得保留的设计

CC 的两阶段拆分是合理的：

1. 第一层做能力、字段、主题和动作选择；
2. 中间 Search 由确定性代码执行；
3. 第二层只做候选方案编号选择；
4. 代码重建最终模板调用树；
5. 编译器、校验器和渲染器负责保证输出可用。

这比让 3B 直接生成完整模板调用树稳定得多。第二层从“生成受限调用树”改成“候选列表中的编号选择”，是当前最有价值的端侧适配改造。

GD 的“语素规划 → 能力绑定 → 确定性布局和渲染”方向也合理。把字段绑定、布局预算、动作数量和组件渲染留在代码侧，可以减少小模型直接生成组件、CSS、数据绑定和英文键的负担。

### 需要调整的定位

当前数据集不能同时承担三件事：

- 训练模型；
- 验证工程流程；
- 证明自然语言泛化。

建议拆成三个资产层。

| 资产层 | 目的 | 是否用于汇报模型准确率 |
|---|---|---|
| 工程回归集 | 验证格式、编译、Search、渲染和接口 | 否 |
| 正式 SFT 集 | 学习真实表达到结构化输出的映射 | 训练使用 |
| 冻结评测集 | 评估未见表达、边界和安全降级 | 是 |

现有 CC/GD 数据归入第一层最合适。经过人工清理和重新扩写后，合格样本才能进入第二层。

## 正式数据集的整改方案

### 第一步：保留并标记现有数据

不删除现有产物，在数据卡中追加：

- `dataset_role: synthetic_bootstrap`；
- `not_for_generalization_claim: true`；
- `surface_templates: 36` 或实际模板数量；
- `human_review: pending`；
- `leakage_check: required`。

这批数据继续用于：

- 训练脚本冒烟；
- LoRA/QLoRA 管线冒烟；
- 推理格式验证；
- 批量渲染筛查；
- 端到端回归。

### 第二步：重建自然语言训练集

每一个能力或语素骨架都应补充多种独立表达，而不是只替换字段名。建议至少覆盖：

- 简短口语；
- 同义词；
- 省略主语；
- 长句和上下文表达；
- 错别字；
- 时间词和指代词；
- 否定；
- 纠正；
- 多字段组合；
- 跨领域请求；
- 请求动作；
- 明确不需要动作；
- 注册表外请求；
- 领域内但字段不存在的请求。

每个样本至少保留以下审计字段，但审计字段不能进入模型输入：

```json
{
  "id": "gd-natural-0001",
  "source": "human|reviewed_synthetic",
  "bucket": "paraphrase_longtail",
  "prompt": "手机还剩多少格电？",
  "expected": {
    "domain": "DEVICE",
    "morphemes": [
      {
        "keys": ["phone.battery.level"],
        "role": "PRIMARY"
      }
    ]
  },
  "notes": "“多少格电”映射到电量百分比"
}
```

CC 中必须把“能力候选上下文”和“用户原话”分开审查。能力候选可以包含系统注册信息，但 `USER REQUEST` 应尽量保持真实用户表达，不应把 schema 解释直接写进用户话语。

### 第三步：建立正式冻结集

GD 当前仓库主要存在冻结集模板，正式的 `frozen_set_v1.jsonl` 仍需要人工编写和逐条审核。CC 的 TaskSpec 冻结样本也应继续保持独立，不能自动扩展后直接视为人工测试集。

冻结集建议覆盖以下分桶：

| 分桶 | 目标 |
|---|---|
| 单领域明确字段 | 检查基础字段识别 |
| 只说领域 | 检查默认字段策略 |
| 近义词和口语 | 检查真正的语义泛化 |
| 长句和错别字 | 检查鲁棒性 |
| 否定和纠正 | 检查边界理解 |
| 跨领域 | 检查拆分和取舍 |
| 不支持能力 | 检查不乱绑定 |
| 领域内超纲字段 | 检查不幻觉 |
| 多动作 | 检查动作上限和取舍 |
| 无操作请求 | 检查动作幻觉 |

冻结集必须满足：

1. 不进入训练集；
2. 不使用训练句式的简单改写；
3. 目标答案组合尽量不与训练集重复；
4. 每条记录由人工确认输入和答案的对应关系；
5. 每次定稿后只追加，不修改旧版本。

### 第四步：增加四层泄漏检查

每次组装训练集后，至少执行：

1. **文本级去重**：完全相同的用户请求；
2. **近重复去重**：编辑距离、归一化文本或 n-gram 相似；
3. **事实级去重**：相同领域、字段、动作和答案组合；
4. **场景级切分**：同一案例、骨架或业务场景不得跨 split。

只有四层检查都通过，才能把分数用于模型比较。

## CC 和 GD 的训练任务建议

### CC 第一层

继续保留结构化输出：

```json
{
  "theme": "...",
  "capability": "...",
  "fields": ["..."],
  "action": ["..."]
}
```

但应重点增加真实表达和负例。能力候选列表可以由服务端注入，用户请求本身不能复制候选字段描述。

训练目标应关注：

- 字段召回率；
- 字段精确率；
- 动作幻觉率；
- 主题选择准确率；
- 跨业务误选率；
- JSON 合法率。

### CC 第二层

当前编号选择方案是合理的：

```json
{
  "plan": 2,
  "showIcon": true
}
```

候选方案由代码预先枚举，模型只比较“用户请求想要展示什么”和“每个方案能展示什么”。最终模板树由代码生成。

该层不应重新训练模型生成：

- Template 调用树；
- Props；
- 数据绑定；
- A2UI；
- CSS；
- 事件执行结构。

### GD 语素层

GD 当前让模型输出英文语义键，容易产生拼写错误和注册表外键。更稳的方案是让模型输出注册表候选编号：

```json
{
  "title": "电量",
  "primary": 2,
  "secondary": [5],
  "actions": [1]
}
```

代码再把编号解析为真实键。这样能减少：

- 英文键拼写错误；
- 近义键混淆；
- 注册表外幻觉；
- 小模型对英文语义键的记忆压力。

如果暂时保持 `q` 为英文键，也应在推理阶段使用候选约束、别名归一化和注册表校验，不能直接信任模型字符串。

## 正确的验收方式

正式训练前先跑裸模型基线，再跑微调模型。每次固定：

- 基座模型和量化方式；
- prompt manifest 版本；
- temperature；
- 最大输出长度；
- 是否启用约束解码；
- 训练轮数和 LoRA 配置；
- 评测集版本；
- 评测脚本版本。

报告至少分为三组：

| 组别 | 说明 |
|---|---|
| bootstrap test | 只看工程回归，不解释泛化 |
| unseen-combination test | 看未见案例组合上的稳定性 |
| frozen natural-language test | 作为正式自然语言能力指标 |

GD 还应把“该做”和“不该做”分开统计：

- 正确绑定率；
- 漏绑率；
- 错绑率；
- 未注册能力误绑定率；
- 无操作请求的动作幻觉率；
- JSON 合法率；
- 最终可渲染率。

CC 还应把第一层和第二层分别报分，不能只给端到端一个总分。因为两层错误的来源不同：

- 第一层错，通常是能力或字段理解错；
- 第二层错，通常是候选方案比较错；
- Search、编译和渲染错误，应单独归为代码链路问题。

## 推荐执行顺序

1. 将当前 CC/GD 数据卡标记为 bootstrap；
2. 完成 GD 正式 frozen set v1；
3. 完成 CC 和 GD 的文本、近重复、答案组合泄漏检查；
4. 从现有案例中抽取可保留的结构样本；
5. 人工重写一批真实自然语言种子；
6. 使用模型扩写，再逐条人工审核；
7. 按场景和语义组合重新切分；
8. 跑裸模型基线；
9. 用小规模 SFT 验证训练收益；
10. 在 frozen 集上比较训练前后变化；
11. 通过冻结集后，再扩大训练规模和进行量化部署。

在第 8 步之前，不应根据当前合成 test 分数判断模型是否“学会了自然语言理解”。

## 最终判断

当前工程的方向是可行的，确定性 Search、模板枚举、编号选择、注册表校验和渲染后处理都值得继续保留。

需要收敛的是数据集的身份和验收口径：

> 当前数据证明了工程链路可以运行；新的自然语言数据和独立冻结集，才负责证明模型是否真的理解用户意图。
